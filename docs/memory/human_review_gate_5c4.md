## What was built

- **`src/review/` package** (new): `change_snapshot.py` (`ChangeSnapshot` — `run_id`/`changed_files`/`mutation_count`/`test_results`/`diff_path`, frozen dataclass), `change_snapshot_builder.py` (`ChangeSnapshotBuilder.build()` parses a Run's `events.jsonl`), `snapshot_repository.py` (`SnapshotRepository.save()/load()` persists to `change_snapshot.json` in the run's own directory — takes `run_directory: Path` directly rather than `run_id` alone, since `run_id` doesn't identify its owning task), `review_policy.py` (`requires_review(agent_id, snapshot) -> bool`: only `agent_id == "agent-coder"` AND `mutation_count > 0`), `review_report.py` (`ReviewReport` — `run_id`/`summary`/`changed_files`/`risks`/`approved`, `summary`/`risks` are permanent placeholders until a future Reviewer Agent), `review_service.py` (`ReviewService.build_report()` — deliberately pure/stateless, no I/O, just `ChangeSnapshot` + `approved: bool|None` → `ReviewReport`), `NOTES.md` (documents a known future schema evolution: `test_results` is dict-keyed-by-tool-name today, would need to become a list if a Run ever needs to run multiple distinct test commands and keep every result instead of last-call-wins).
- **New Run statuses**: `awaiting_review`, `approved`, `rejected`. **No `RunStatus` Literal type was created** — confirmed the codebase has never had one (`RunDefinition.status` has always been plain `str`, even through the 5B-6 state-machine work), so these are handled the same informal way as existing statuses (plain string comparisons, `RESUMABLE_STATUSES`-style sets). `approved`/`rejected` are deliberately excluded from `RESUMABLE_STATUSES` — a Run awaiting/decided review isn't a crash, `resume` must not touch it (regression-tested).
- **`RunService.execute()`**: after writing output/summary, builds the `ChangeSnapshot` from the run's `events.jsonl`, **persists it immediately** via `SnapshotRepository` (this is the key design point: `review` later shows state *as of when the run finished*, not a live recomputation — if someone hand-edits the repo afterward, `review` output doesn't change), then `requires_review()` decides the terminal status. `run.json.metadata` always carries `review_required`/`changed_files` (even when `False`/`[]`, not only on the review path).
- **`RunService.get_run(run_id) -> (task, run)`** (public, wraps the existing private `_find_task_for_run`) and **`decide_review(run_id, approved: bool) -> RunDefinition`** (guards `status == "awaiting_review"`, transitions to `approved`/`rejected`).
- **New `review` CLI command** (`python -m src.main review <run-id>`) in `main.py`: prints Status/Changed files/Mutations/Tests/Diff/AI Summary sections, gracefully handles a missing snapshot (`SnapshotNotFoundError` caught locally, prints a message, no crash — matters for any run predating this feature), only shows the `Approve? [y/N]` prompt when `status == "awaiting_review"`. `y`/`yes` → approve, `n`/`no`/`reject` → reject, anything else (including bare Enter) → no state change, stays `awaiting_review`. Also fixed `_print_run_result()` which previously always printed `"Completed run: ..."` regardless of actual status — now branches on `result.status`.
- **Necessary fix in `llm_executor.py`** discovered while building `ChangeSnapshotBuilder`: the `tool_result` event never carried `exit_code`/`timed_out` at all (not nested under a `metadata` key as a naive spec assumed — genuinely absent). This mattered because `run_test`'s `ToolResult.success` is *always* `True` even when the test failed (5C-3D's deliberate design — test failure ≠ tool failure), so without `exit_code` reaching `events.jsonl`, there was no way to recover pass/fail from the event log at all. Fixed by adding `"exit_code": result.metadata.get("exit_code")` / `"timed_out": result.metadata.get("timed_out")` to the tool_result event, same generic `.get()` pattern as `duration_ms`. Side effect: historical `events.jsonl` files from before this fix (e.g. `tasks/task-run-test-loop/runs/run-001`) don't have these fields — a test covering that historical file only asserts `changed_files`/`mutation_count`, not `test_results`.

## Known caveat surfaced during manual CLI verification (not fixed, just documented)

`run_id` is only unique **within** a task — `get_run()`/`_find_task_for_run()` return the first task (alphabetically by directory name) whose `runs/` contains a matching id, silently. Hit this directly during manual testing (created a scratch run also named `run-001`, `review run-001` resolved to a different, pre-existing task's `run-001` instead). Pre-existing behavior shared with `resume`, not introduced by 5C-4. A verification write-up for this was originally saved to `tasks/task-5c4d-review-cli-verification/` but **the user deleted that directory before the commit** (asked explicitly, chose "leave it out" rather than recreate) — so that specific manual-verification record does not exist in the repo. The real code fixes/tests from 5C-4 are still committed and pushed; only the extra documentation task was dropped.
